**Breakpoints that fire are reported bound** — on a JavaScript launch session, `list_breakpoints` kept reporting `verified: false, message: "Unbound breakpoint"` for breakpoints the debuggee had demonstrably stopped on: js-debug verifies a source-mapped `src/x.ts` request under its *generated* `dist/x.js` path and line, which matched nothing in the store, and sends no verification at all for a `node_modules` file. The child session's provisional breakpoint ids are now stamped as the record's `adapterId` as soon as its replay answers (the parent's colliding id space stays excluded, #495), so the later verification under a generated location binds the right record — reported as `boundFile`/`boundLine` beside the untouched request, by every path that writes a location — and a `stopped` event's `hitBreakpointIds` marks the breakpoints it names verified for every adapter that sends the field, dropping the stale unbound message. Such a record carries `verifiedBy: "hit"` and an adapter answer of "unbound" for it is not evidence it stopped firing (js-debug answers that on every re-send for a `node_modules` location it cannot map to a source). Windows paths spelled with forward and backward slashes now match. The js function-breakpoint bridge merges the line-breakpoint ids into a co-firing stop instead of replacing them (#673)
