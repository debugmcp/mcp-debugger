**`start_debugging` answers the same way in every language, after one short hold** — once the program is launched, the call holds its answer briefly for the program's first stop and reports whichever comes first: `paused` with the reason, `stopped` with the exit code, or `running` with `pending: true`. That is now one rule for all ten languages. Before, JavaScript launches answered `running` as soon as the program was configured, even with breakpoints armed, so the launch response could not be read as "where did it stop" the way it could elsewhere; and every other language waited up to 30 s when something was armed, which blocked the caller for exactly the case where it has to act first — a breakpoint in a server's request handler that only a request can reach. The hold is about a second, sized from measured launch-to-first-stop latency (at most 172 ms across the nine language adapters on an idle machine, 678 ms with every core saturated), and is deliberately kept out of the tool contract: it is not a limit on the program, nothing is cancelled when it elapses, breakpoints stay armed, and `wait_for_stop` blocks until the stop arrives. A `stopOnEntry` launch is still answered at its entry stop however long that takes, and a `noDebug` launch follows the same rule (it is answered by its exit or by the hold, in debugger-off terms). What changes for callers: a JavaScript launch whose breakpoint is reached as the program starts keeps answering `paused`, and one that used to answer a bare `running` now carries `pending: true`; in the other languages a breakpoint first reached more than about a second after launch answers `pending: true` instead of holding the call open — call `wait_for_stop`. The `pending` message no longer states a duration. A launch answered while its program is still running no longer re-sends the breakpoints to the adapter afterwards — the send the launch itself made stands, and `list_breakpoints` reports them verified in all nine languages without it; the re-send is kept for a launch that is paused, because a running program may already be gone when it arrives (a logpoint that had fired then read `verified: false`, #856). So that nothing is lost by it, a function-breakpoint request the adapter rejects before launch is now echoed by the proxy with the debugger on as well as under `noDebug`, and the launch answer quotes it as a refusal rather than advising to check the symbol name. `AdapterPolicy.isSessionReady` is removed: no policy has a say in when a launch answers (#823, #815)
