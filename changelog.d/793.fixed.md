**`start_debugging` and `set_breakpoint` accept a session whose program has exited or that has only dry-run** — a session is lifecycle-terminated after a run to completion and after a `dryRunSpawn: true` check, and the server refused both tools on it with `Session is terminated` while `restart_debugging`, `remove_breakpoint`, `clear_breakpoints`, `list_breakpoints` and `get_output` already accepted it — so the "check the spawn, then launch" and "ran past my breakpoint → set an earlier one → restart" loops each needed a fresh session. A present-but-terminated session is now the between-launches state: `start_debugging`, `restart_debugging` and every breakpoint tool take an existence-only gate (a breakpoint set between launches is stored `verified: false` and applied by the next launch, whose response and `list_breakpoints` carry the adapter's own answer), and only the tools that need a live debuggee — stepping, `continue_execution`, `pause_execution`, `list_threads`, stack/scopes/variables/evaluate, `get_source_context`, `expose_session` — still answer `Session is terminated` (#793, #806)
