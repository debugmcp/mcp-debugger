**A JavaScript step that leaves a function through `return` inside `try … finally` lands in the caller.** V8 can lose such a step (measured on V8 12.4, 13.6 and 14.6 with a bare CDP client): a `step_out` of the function, a `step_over` off its `finally` block, and a `step_out` of an `async` function with that shape all answered `Step completed as session exited.` while the program ran on. Node's own module loader returns that way too, which is how a `step_into` on a `require` line was lost. Where V8 can lose a step, the server no longer counts on V8 alone to come back to the frame below: it sets temporary breakpoints on that frame, and whichever pauses first is the landing. That is something the server does in your process: at most 24 temporary breakpoints per guarded frame, for the length of one step, removed when the step ends however it ends. One rule says when, for all three steps: from your own code only where the function has a `finally` clause and cannot suspend before it exits from the paused line (a function that awaits does not return to its caller, and V8 keeps a step across an `await`); from skipped code always; never on the frame being stepped in. The breakpoints name one call only while the frame they guard stays on the stack. Where it does not (it was waiting at an `await` for the call the step leaves, or it is the function awaiting an `async` one the event loop resumed) the step stops in whichever call of that function runs next, and the answer says so (#1166). Not covered: a `step_over` across the first load of a module that has a breakpoint in it still runs on (#1162). (#1161)
