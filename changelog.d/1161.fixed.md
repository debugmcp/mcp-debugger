**A JavaScript step out of a function that returns inside `try … finally` lands in the caller.** V8 loses such a step (measured on V8 12.4, 13.6 and 14.6 with a bare CDP client; also a `return` out of a `for … of` loop and out of a function with a `using` declaration): a `step_out` of the function and a `step_over` off its `finally` block answered `Step completed as session exited.` while the program ran on. Node's own module loader returns that way too, which is how a `step_into` on a `require` line was lost. The server now sets temporary breakpoints on the frame such a step returns to, and whichever pauses first is the landing. That is something the server does in your process: a temporary breakpoint on every break location of the frame the step returns to (a function with more than 100 is not guarded), for the length of one step, removed when the step ends however it ends. The step then lands at the caller's next break location after the call. The breakpoints are set only where a hit proves the step came back: the function being left is a plain one (not `async`, not a generator), and the frame it returns to stays on the stack until it reaches one (a caller that awaits the call does not). A step V8 loses in an `async` function or a generator is not rescued: a breakpoint below a function that can suspend cannot tell it returning from it pausing at an `await`, so that step stays lost as before (#1174): it answers `pending: true` with a sentence naming the case while the program keeps running, and `Step completed as session exited.` when it ends first. Not covered either: a `step_over` across the first load of a module that has a breakpoint in it (#1162). (#1161)
