**A JavaScript step that leaves a function through `return` inside `try … finally` lands in the caller.** V8 can lose such a step (measured on V8 12.4, 13.6 and 14.6 with a bare CDP client): a `step_out` of the function, a `step_over` off its `finally` block, and a `step_out` of an `async` function with that shape all answered `Step completed as session exited.` while the program ran on. Node's own module loader returns that way too, which is how a `step_into` on a `require` line was lost. Where a step can leave a frame that way, the server no longer counts on V8 alone to come back to the frame below: it sets temporary breakpoints on that frame, and whichever pauses first is the landing. That is something the server does in your process: at most 24 temporary breakpoints per guarded frame, for the length of one step (every `step_out`; a `step_over` or `step_into` from a function whose text has a `finally` clause; a step that walks through skipped code), removed when the step ends however it ends. Left to V8 on purpose: a function that returns to itself (`step_over`, `step_into`); and, in a function that can suspend, any line that itself awaits or yields, so a `step_over` on an `await` that is the last thing a function does before it leaves through `finally` can still be lost. An `async` function the event loop resumed returns to the function awaiting it, which is not on the stack: V8's own step finds the call that awaited, and only where V8 loses the step does the server guard the awaiting function, in whichever call of it runs next; that answer says the stop may be another call's. Not covered: a `step_over` across the first load of a module that has a breakpoint in it still runs on (#1162). (#1161)
