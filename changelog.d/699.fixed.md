**A JavaScript launch binds a source-mapped breakpoint before the line runs** — a breakpoint on a `.ts` line that executes at module load (a top-level statement, or a call made while the module loads) was verified by js-debug only after the line had already run, so the launch reported `state: "stopped"` with the breakpoint `verified: true` and no stop; `dapLaunchArgs: { stopOnEntry: true }` was the workaround. Two causes, both on our side. js-debug's breakpoint predictor — the mechanism VS Code relies on to pre-bind a `.ts` breakpoint at its generated location before the program starts, for the entry script and for every module required later — needs a workspace root, and the launch never sent one, so it never ran. And the `pauseForSourceMap` we forced on every launch does not fire for a CommonJS entry module under Node 24 (it does for an ES module), while its presence makes js-debug skip the predictor. The launch now sends `__workspaceFolder` (an explicit value, else `cwd`, else the program's directory; relative `outFiles` resolve against it) and leaves `pauseForSourceMap` at js-debug's own default for compiled `.js` programs, keeping it on for a `.ts` program run through a transpiler; an explicit `pauseForSourceMap` wins. With the root set js-debug also applies its default `sourceMapPathOverrides` (`webpack:///` and similar) that were previously filtered out. Verified with the checked-in `typescript_test` fixture compiled as ES2015/CommonJS and on this repo's own `dist/index.js`, where a breakpoint on a top-level line of `src/cli/port.ts` — a module the CLI requires while starting — now fires (#699)
