**One verdict on which thread a stop is anchored on** — the attach controller's thread rescue and the stack resolver's sibling scan, previously two copies with different predicates and bounds, now share `selectStopAnchor`: the reported thread first, then a thread named `main`, then listed order; a thread reaches the program when a frame both names a source and is one the language policy calls the program's. Caller-visible consequences: the resolver's scan now gives every unwind its own 3 s timeout; a `threadId`-less `get_stack_trace` answered from a thread other than the one the stop was reported on carries the note `The stop was reported on thread X; inspection is anchored on thread Y.`; `get_stack_trace` results carry `noProgramFrame: true` when no frame of the shown stack is program code (#904)
