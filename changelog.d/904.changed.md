**One verdict on which thread a stop is anchored on** — the attach controller's thread rescue and the stack resolver's sibling scan, previously two copies with different predicates and bounds, now share `selectStopAnchor`: the reported thread first, then a thread named `main`, then listed order; a thread reaches the program when a frame both names a source and is one the language policy calls the program's. For an attach that means a frame whose source has a name but no path (a Java class without debug info) now counts, while a thread whose sourced frames are all runtime by the policy's reckoning (glibc or winpthreads plumbing with a system path) no longer does, so the scan moves on to the thread in `main`. A Go `pause_execution` reported on a goroutine parked entirely under `/runtime/` now moves to a goroutine in the program's code the same way. Caller-visible consequences: the resolver's scan now gives every unwind its own 3 s timeout; a `threadId`-less `get_stack_trace` answered from a thread other than the one the stop was reported on carries the note `The stop was reported on thread X; inspection is anchored on thread Y.`; `get_stack_trace` results carry `noProgramFrame: true` when no frame of the shown stack is program code (#904)
