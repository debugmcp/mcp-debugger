**Attach addressing contract** — each adapter now declares on its factory metadata (`modes.attachBy`) which `attach_to_process` addressing forms it accepts (`processId`, `port`, a debugger URI under `adapterConfig`), and the core refuses any other form by name before the session changes state: a `processId` on a port-only language (Python, Ruby, Java) or on Dart answers with the adapter's own recipe for opening a port or a VM-service URI, a `port` or a remote `host` on a PID-only language (C/C++, COBOL, .NET) says so, a `processId` beside a remote `host` is refused on every language (a PID is a process on this host), and a request naming neither on a language whose forms are those two is refused as "needs port" / "needs processId" instead of failing later with the debugger's defaults. The session stays usable after a refusal, and `list_supported_languages` shows the forms as `modes.attach.by`. **Heads-up:** requests that carried an extra key the adapter silently dropped — `processId` beside a `port` on Python/Ruby/Java, a `port` or remote `host` beside a `processId` on C/C++/COBOL/.NET — are refused now; the extra key never did anything, so drop it. Previously the top-level keys reached each adapter's transform, which dropped what it did not use silently — the class behind #450, #466, #871 and #895. The `processId` an adapter consumes (C/C++, COBOL, JavaScript) is no longer reported as an ignored `adapterConfig` key (#903)
