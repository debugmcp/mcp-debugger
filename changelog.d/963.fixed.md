**A slow-starting debug adapter no longer fails the launch with `ECONNREFUSED`, and a failed launch is reported once** — a launch whose debug adapter takes longer than ~12 s to start listening (rdbg on a loaded Windows runner) used to fail with `Failed to connect DAP client: connect ECONNREFUSED` while the adapter was still booting: the proxy's connect window was a fixed 60 attempts; it now ends only when the adapter process exits (at once, quoting the exit code and its last stderr lines) or when the launch's 30 s initialization deadline passes, whose stage-aware message the caller then gets. Direct-connect attaches (a remote rdbg/debugpy already listening) keep the previous 12.5 s window. A launch that fails after its adapter started was reported twice — the proxy worker sent a second copy after its teardown, with `adapter PID=none exitCode=n/a` in place of the real PID and exit code, and that degraded copy overwrote the first as the session's last proxy error. And the worker's stdout pipe was never read by the parent, so an embedder that does not silence console output (the server CLI does) had a worker that blocked solid, deaf to IPC, once its console transport had written 64 KB: the parent now drains it, and the worker's loggers skip the console transport altogether, so the per-session `proxy-<sessionId>.log` is its log and nothing fills a pipe no one reads (#963, #966, #967)
