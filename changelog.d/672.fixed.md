**A breakpoint inside a dependency now inspects the frame it stopped in** — with `node_modules` frames hidden by default (#661), a JavaScript breakpoint or step that landed inside a dependency of a running server was invisible: `get_stack_trace` showed only the async ancestors with a bare "N internal frame(s) hidden", and `get_local_variables` / `evaluate_expression` silently anchored on the first *visible* frame — an `app.listen` ancestor V8 cannot evaluate in — so locals came back empty and evaluate failed with "Unable to evaluate on async stack frame". The shared frame resolver now keeps the stopped thread's paused frame as frame 0 on a breakpoint or step stop (for every language policy that filters frames), with a `note` saying so; after a `pause` or an exception — stops that routinely land in runtime frames where the first user frame is the useful one — it stays hidden but the `note` names it and its `frameId`. `evaluate_expression` now also reports the `frame` it used, on success and on failure. `step_*` and `pause_execution` derive their `location` from the same stack, so a step that lands in a dependency now reports that location rather than its caller (#672)
