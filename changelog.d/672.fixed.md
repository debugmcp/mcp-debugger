**A breakpoint inside a dependency now inspects the frame it stopped in** — with `node_modules` frames hidden by default (#661), a JavaScript breakpoint or step that landed inside a dependency of a running server was invisible: `get_stack_trace` showed only the async ancestors with a bare "N internal frame(s) hidden", and `get_local_variables` / `evaluate_expression` silently anchored on the first *visible* frame — an `app.listen` ancestor V8 cannot evaluate in — so locals came back empty and evaluate failed with "Unable to evaluate on async stack frame". The shared frame resolver now reports such a frame as `pausedFrame` and keeps it as frame 0 on a breakpoint or step stop (a `debugger;` statement, which js-debug reports as a pause, now counts as a breakpoint), or whenever the language policy finds an async boundary between it and the first visible frame; after a `pause` or an exception with a synchronous caller visible — stops that routinely land in runtime frames where the first user frame is the useful one — it stays hidden and the `note` names it. `get_stack_trace` gains `pausedFrame`; `evaluate_expression` reports the `frame` it used, on success and on failure; `get_local_variables` names both anchors when a kept frame had no locals. `step_*` locations follow the same rule; a `pause_execution` that lands inside a hidden frame still reports the first visible frame as its `location` (#672)
