**A refused live breakpoint re-send now leaves the debugger's answer on the breakpoints** — when a `set_breakpoint`, `remove_breakpoint` or `clear_breakpoints` on a live session had its DAP re-send refused (debugpy's `Server is not available` under `noDebug`, a path the remote rdbg cannot open, …), the adapter's words reached only that one response's `warning`; `list_breakpoints` showed the breakpoints as a bare `verified: false`, the run-to-completion summary named them with no reason, and the launcher's and attach's post-handshake re-send discarded the answer altogether. The refusal is now stamped onto every breakpoint the re-send covered (`message`, `verified: false`, the way a refused pre-launch set is echoed) — except one a stop already proved bound, or a child-verified js-debug one — the post-launch and post-attach re-send warnings join the launch/attach result's `warning`, a refused pre-launch function-breakpoint set keeps its message too, and a `set_breakpoint` response no longer repeats the adapter's text twice (#754)
