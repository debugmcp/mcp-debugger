**Windows: a wedged Dart/Flutter or .NET adapter no longer leaves its tool tree running when the session closes** — the Dart bridge and the netcoredbg bridge ended their adapter with `cp.kill()` when the proxy worker's socket went away, which on Windows is `TerminateProcess` on the direct child alone; the Dart SDK launcher (`dart.exe` → `dartvm.exe` → `flutter.bat` → … → the app, DDS, the frontend server) and netcoredbg's launched debuggee were re-parented and kept running, and the worker's own tree kill then found an adapter that had already exited. Both bridges now end the child with `taskkill /T /F` on Windows first (the proxy worker's own idiom), fall back to the plain kill if the child is still there after 300 ms or taskkill cannot be started, and never touch a child that has already exited (its pid may be reused); POSIX keeps `cp.kill()`, where the worker's process-group kill covers the tree. The ordinary close is unaffected (the Dart adapter stops the app on `terminate` and exits by itself, #885); this is the path a wedged adapter takes. The netcoredbg bridge gains the exited-child guard it lacked (#937)
