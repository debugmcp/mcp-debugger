**JavaScript child processes are debugged by default on launch and verified-local attach** — a Node launch now sends js-debug `autoAttachChildProcesses: true` unless the caller says otherwise; every attach form, including `processId`, defaults it on only when the inspector target can read both a temporary server-side probe file and the installed js-debug bootloader files. An unverified target defaults it off with a warning, preventing a server-local bootloader path from breaking later forks in a remote or container target; loopback addresses and shared PID namespaces alone do not prove filesystem access. An explicit attach `true` is retained for callers that ensure the target and its children can load the server's js-debug bootloader and reach its debugger endpoint. With child auto-attach enabled, every Node process the program starts (`fork()`, `spawn(process.execPath, …)`, a `cluster` worker, a grandchild) is reported and becomes a child debug session: listed with `parentSessionId`, stopping on the parent's breakpoints, reported by the parent's `wait_for_stop` with `sessionId` naming it. Each child counts against `DEBUG_MCP_MAX_CHILD_SESSIONS` (default 32); beyond the cap a fork is released by a throwaway attach to run undebugged rather than parked (#501). Opt out per launch with `dapLaunchArgs: { autoAttachChildProcesses: false }`, per attach with `adapterConfig: { autoAttachChildProcesses: false }` (the children then run untouched, as before), or server-wide with `DEBUG_MCP_MAX_CHILD_SESSIONS=0`. A launch child's output is on the launch session's buffer (`get_output` answers `outputOn`); an attach root's children keep their own console output (#1005, #1082).
