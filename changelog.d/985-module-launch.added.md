**Python launches can run a module** — `start_debugging { scriptPath, dapLaunchArgs: { "module": "pytest", "cwd": "/proj" }, args: [...] }` now reaches debugpy as a `python -m pytest` launch. Every launch used to carry `program`, filled from `scriptPath`, and debugpy refuses the pair (`"program", "module", and "code" are mutually exclusive`), so a module launch could not be expressed at all. The Python policy now declares its launch-target keys (`program`, `module`, `code`), the connection manager fills `program` only when the launch config names no target of its own, and the Python launch transform drops `program` beside a `module` or `code` target and says so in the launch answer (`dapLaunchArgs.module: launched as a module (python -m); program is not sent …`). `scriptPath` still names an existing file — the package's `__main__.py`, or the test file a `pytest` run is about — and `cwd` is what `-m` puts on `sys.path`: for a module or code launch it defaults to the directory above the top-most package containing `scriptPath` (the script's directory, the program-launch default, is inside the package, where `python -m modpkg` fails), the launch answer names the directory chosen, and an explicit `cwd` wins — the project root for a pytest run. A dry run reports such a launch's `data.script` as `module: <name>` or `code: …`. The first milestone of one-call failing-test debugging (#985)
