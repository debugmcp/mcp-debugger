**A default JavaScript attach to an idle Node server no longer freezes it.** With a breakpoint set, `attach_to_process` on a server that was running nothing left the server frozen and spinning a full core: the session kept reporting `running`, the breakpoint stayed unbound, and `close_debug_session` answered `released: true` while the server stayed frozen (two runs in three on Node 24). A pause sent to a program that is executing nothing stays armed in V8 and fires inside the next code that runs there, and that was js-debug's own code, which the attach's breakpoint re-send made it evaluate in the target. Now a pause always has something to land on: before it requests one, the server schedules a single no-op timer in the target (`setTimeout`, 150 ms, unref'd), and the pause lands when it fires. `attach_to_process` and `pause_execution` on an idle Node program therefore answer `paused` in `process.processTimers`, with the `note` that no program frame is active, where they used to answer `running` with `pending: true`; this holds for launched programs too. (On a loaded machine the pause can still land inside js-debug's own start-up evaluation, on a sourceless `<anonymous>` frame with the same note.) The attach also re-sends breakpoints before it requests the pause instead of after, for every adapter. Where the timer cannot wake the program (it is busy in native code, or it replaced `setTimeout`), the answer is still `pending: true`, and breakpoint requests made while that pause is pending answer `warning: "Held: a pause is pending on this session…"` and are sent when the program stops. A breakpoint request that js-debug's target session does not answer in time now says so in `warning` instead of only in the log, and an attach whose re-send went unanswered does not request the pause.
