**`close_debug_session` on an attach session waits up to 10 s for the debug adapter to release the target, as `detach_from_process` does** — a target started with `python -m debugpy --listen` has one debug adapter, started once, which owns the port; it answers a `disconnect` only once the target's interpreter is free, and it exits when its client closes the connection before that answer is written. The close gave it 1 s and then closed the connection, so closing a session while the target held its interpreter for longer (a long C call, a backtracking regular expression) left the service running with its debug port gone (measured with 0.27.0: a close during a 4 s hold, the adapter process gone, connections refused). The close now sends the same release as `detach_from_process`, under the same 10 s bound, before the session's worker is stopped. When the adapter does not confirm it in time, for a close or a detach, the answer says so: the release was not confirmed within 10000 ms, the connection was closed, a debug port that belongs to the target may have closed with it, and whether the process is still running is not known. A target busy for longer than 10 s can still lose its port; the rest is tracked in #1325 (#1325)
