**An adapter whose import fails is no longer reported as "Adapter not installed"** — a missing transitive dependency (measured: `dotenv` absent next to an installed `@debugmcp/adapter-javascript`) raised the same module-not-found code as an absent package, so the loader said `Adapter not installed. Install with: npm install @debugmcp/adapter-javascript`, discarded the import's own error while trying its fallback paths, `list_supported_languages` still reported the language's launch as available, and `start_debugging` then answered `No debug adapter registered for language: javascript. Available: … javascript …` — the language listed as available in its own failure, `dotenv` never named. The loader now keeps every attempt's error and reports the first that names something other than the specifier it was asked for, asks the package resolver whether the package is on disk (its entry or its `package.json`) before calling it "not installed", and otherwise says `The package is installed but importing it failed: Cannot find package 'dotenv' imported from … — its dependency 'dotenv' is missing or broken. Reinstall it (npm install @debugmcp/adapter-javascript) or rebuild it.`; that reason travels as the `cause` of the registry's error, whose message reads `No debug adapter could be loaded for language: javascript — …` with the failed language left out of `Available`; `list_supported_languages` reports both modes unavailable with the same words, `create_debug_session`/`start_debugging` refuse with them before any proxy is spawned, and `mcp-debugger doctor` agrees (#795)
