**A `noDebug` launch completes on python, go and C/C++ instead of dying in initialization** — `dapLaunchArgs.noDebug: true` on an adapter that honours the flag (#710) used to fail every time: the proxy worker waited for the adapter's `initialized` event to run the configuration phase (breakpoints, exception filters, `configurationDone`), and an adapter that is not debugging — debugpy, Delve — correctly never sends one, so a short script ended `success: false` with "Proxy exited during initialization. Code: 0" although it had run and exited 0, and a server hit the 30 s init deadline; CodeLLDB does open the phase but refuses what is sent in it ("Not supported in noDebug mode"), which read as "Error in DAP sequence" and tore the session down. Under an honoured `noDebug` the worker now reports the launch configured on the `launch` response (skipping the two-phase go/java waits too), and a configuration phase the adapter opens anyway still runs unchanged — the adapter's own answers stand — with a refused request logged rather than fatal and `configurationDone` still sent (CodeLLDB withholds the launch response until then). The three launches now end `stopped` with the exit code, the program's output and the #710 warning; js-debug is unchanged and the adapters that ignore the flag still pause at their breakpoints. One adapter quirk surfaced on the way: under the flag Delve runs the binary through Go's `exec`, so on Windows it needs its `.exe` extension (#746)
