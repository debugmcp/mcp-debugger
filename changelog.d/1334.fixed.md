**A Python logpoint that cannot evaluate is refused at `set_breakpoint` time, with the form that works** — debugpy evaluates the text inside each `{...}` group of a `logMessage` as a Python expression at every hit, not as an f-string field, so `{entry!r}`, `{total:.2f}` and `{x=}` were accepted and then logged `invalid syntax (<string>, line 1)` (or `invalid decimal literal (<string>, line 1)`) at each hit. `set_breakpoint` now refuses a group whose top level holds an f-string conversion (`!r`, `!s`, `!a`), a format spec or the `=` debug form, and names the replacement: `{repr(entry)}`, `{format(total, '.2f')}`, `x={repr(x)}`. A group that reads as a dict with a quoted key or several pairs (`{"k": total}`) is told that a dict needs its own braces, `{ {"k": total} }`; a spec written straight after the colon (`{x:10}`) gets the format form only; an unquoted key with a space after the colon (`{k: v}`) gets both, format first. One refusal names up to three groups and counts the rest. Not caught, so debugpy still logs the syntax error at the hit: a brace inside a string literal, which splits the group; a comment; a conversion or spec inside brackets (`{str(x!r)}`); `{x:=^10}`, which reads as an assignment; and any group after one that does not parse on its own, since debugpy joins the groups into one expression (#1334)
