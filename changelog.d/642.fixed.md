**Java launch applies `cwd` and `env` instead of silently dropping them** — the adapter accepted and forwarded both keys, but the JDI bridge never read them, so the debuggee inherited the bridge JVM's working directory and environment with no warning; a program reading a relative data file or a required variable failed with nothing in the response saying why. The bridge now applies `cwd` (`ProcessBuilder.directory`, rejecting a non-directory loudly) and `env` (merged into the child environment; a JSON `null` value removes the variable). Note the deliberate side effect: the session layer has always defaulted `cwd` to the script's directory when a launch passes none, and Java now honors that where it used to be ignored — so a Java debuggee that previously ran in the server's install directory (or `/workspace` in container mode) now runs in its script's directory, matching the other adapters. `cwd`/`env` also left `supportedAttachKeys`: attach never spawns a process, so passing them there now warns as forwarded-unrecognized instead of being silently recognized-and-meaningless.
