**`attach_to_process` anchors on the thread that is in the program** — after a pause-on-attach the session's current thread was the one named `main`, else the first the debugger listed; CodeLLDB on Windows lists threads by id and reports the attach stop on the break-in thread the OS injects, so a C/C++ attach by PID could open on an `ntdll` stack with no source and `get_local_variables` empty until the caller switched threads. The attach now anchors on the first thread whose stack reaches a source file — the reported stop thread tried first, then the `main`-named one, then the rest (at most 16 threads, each unwind under 3 s within a 10 s budget) — and falls back to the old rule when none does; the C/C++ attach test asserts the program's frame is on the default stack. For adapter authors: `transformAttachConfig` may be async (the launcher awaits it), and an adapter can declare `consumedAttachKeys` for `adapterConfig` keys it uses itself so they are no longer reported as ignored (#759)
