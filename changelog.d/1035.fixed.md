**Host and Docker no longer share one build cache entry over a bind mount.** C/C++: the adapter's `.debug-mcp/` cache decided reuse by file times alone, so a `hello.cpp` built on a Linux/macOS host was launched as-is inside the container (same path, same name), where its DWARF named the host's paths and every line breakpoint stayed unbound. Each compile now writes a build record beside the output (`<binary>.build.json`: compiler and version, flags, platform, architecture, whether it was built in the container, the source path as compiled), and a cached binary is reused only when the record matches the current environment and the source is not newer; a binary built before records existed is rebuilt once. COBOL: the builder kept one `latest.json` pointer and one prune pool per program for every environment, so the container's build repointed the host's pointer at a `/workspace/...` path the host cannot read (one rebuild into a `<key>-2` directory per switch), each side's prune deleted the other's directories, and when the container had created a program's directory first the host launch failed outright with `EACCES … mkdir`. Artifacts now live under an environment segment, `.debug-mcp/cobol/<platform>-<arch>[-container]/<name>/<buildKey>/` (`linux-x64`, `win32-x64`, `linux-x64-container`), each environment with its own pointer, prune pool and key directories, and the segment is part of the build key; a pointer that cannot be written is a warning, not a failed build. Caches from the previous layout are not reused or removed (one rebuild per program; the old `.debug-mcp/cobol/<name>/` directories can be deleted). A root-owned `.debug-mcp/` the container created before the host ever built still sends the host's artifacts to its temp directory with a warning: run the container as your own user (`--user $(id -u):$(id -g)`, see `docs/docker-support.md`) and no root-owned file lands in the mount (#1035)
