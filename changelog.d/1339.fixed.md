**Three waits that state a bound now keep it** — each checked its bound only between awaited steps, so a poll interval, a probe or a request still in flight when the time ran out kept the caller waiting past the bound its answer then named. The JavaScript attach by `processId` waited for the inspector after the signal "within 5000 ms" while a `/json/list` probe in flight ran on for up to its own 1,000 ms and an ownership query for up to its own 1,500 ms (measured: a listener that never answers turned a 400 ms wait into 1,127 ms, and an inspector whose ownership query is never answered into 1,632 ms). The implicit stack read's wait for a paused thread's frames ("within 3000ms") sent its `stackTrace` and `threads` requests with the default 30 s request timeout rather than what was left of the window, so a stalled adapter held the read for up to 35 s and then failed with the adapter-timeout error instead of the sentence that names the window; that sentence is now the answer. The worker's wait for the entry stop of a `stopOnEntry` launch (12 s) likewise sent its `threads` and `pause` requests with the default 30 s timeout. All three now run on one shared deadline: every poll interval ends at it, every probe and request is given the time that remains and none starts after it, a request still in flight may answer for 250 ms more (so the worker's own timeout diagnostics still arrive) and is abandoned after that, and the wait leaves no timer or pending request of its own behind when it answers (an abandoned probe's connection is closed by the probe; an ownership query's WebSocket can only be asked to close). A sibling-thread scan begun near the end of the stack read's window now gets what is left of the window rather than a full poll interval, and a sibling found after the window closed no longer moves the session's inspection anchor (#1339)
