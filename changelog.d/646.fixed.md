**Java launches recompile a stale JDI bridge instead of silently running the old class** — `buildAdapterCommand` only compiled the bridge when no `JdiDapServer.class` existed at all, so after editing `JdiDapServer.java` (or a `git checkout` that touched it) every session ran the previously compiled class: new launch keys were dropped, new DAP behavior was absent, and nothing said why. The launch path now goes through the mtime-aware `ensureJdiBridge()` — a fresh class costs two stats, a stale one is recompiled and logged, and a stale one that cannot be recompiled (no `javac`, or a compile error, whose first lines are now captured rather than inherited into the worker's stdio) is used with a warning naming the reason. `validateEnvironment` and `mcp-debugger doctor` report a `JDI bridge source is newer than the compiled class` warning ahead of time. An explicit `JDI_BRIDGE_DIR` is never compared or recompiled; an install that ships only the class is never considered stale (#646)
