**`set_breakpoint` with `line` and `expectedContent` falls back to line addressing on remote or unknown-host attaches, unresolved local-attach paths, and source identifiers** — on a remote attach, an attach whose target host is not known, a local attach whose path is not usable on this host, or a non-file source identifier such as a Java class name, `set_breakpoint {file, line, expectedContent}` used to fail as a JSON-RPC `InvalidParams` error telling the caller to drop `expectedContent` and keep `line`, costing a wasted call on the first breakpoint of remote attach sessions. It now requests the breakpoint at `file:line` by line addressing, keeps the adapter's own `verified` and `message` fields, and adds a `warning` stating that `expectedContent` was not checked and why (while launch and local-attach files that exist on this host and cannot be read — binary, empty, or too large — are still refused). Passing `statement` there (with no `line` to fall back on) is still refused, now as a `{success: false, error, state}` tool answer naming `file` and `line` (and telling the caller to omit `nearLine` too when passed) rather than a protocol error, and `set_breakpoint`'s description (mode-gated under `DEBUG_MCP_BP_ADDRESSING`) and the debugging skill state where content addressing is checked (#1326)
