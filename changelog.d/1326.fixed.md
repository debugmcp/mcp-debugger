**`set_breakpoint` with `line` and `expectedContent` sets the breakpoint by line when the server cannot check the source** — on a remote attach, an attach whose target host is unknown, a local attach whose file is not usable on this host, or a non-file source identifier such as a Java class name, `set_breakpoint {file, line, expectedContent}` used to fail as a JSON-RPC `InvalidParams` error telling the caller to drop `expectedContent` and keep `line`, costing a wasted call on the first breakpoint of remote attach sessions. It now sets the breakpoint at `line` by plain line addressing, answers with the adapter's verdict, and adds a `warning` stating that `expectedContent` was not checked, why, and which line the breakpoint was set at. Passing `statement` there (where there is no `line` to fall back on) is still refused, now as a `{success: false, error, state}` tool answer naming `file` and `line` rather than a protocol error, and the `set_breakpoint` descriptions (mode-gated under `DEBUG_MCP_BP_ADDRESSING`) and debugging skill state up front where content addressing applies and that a remote attach takes `file` and `line` with line numbers from the file as the target has it (#1326)
