**Detaching from a CodeLLDB target on Windows no longer kills it after a step** — CodeLLDB's Windows detach resumes every thread with the resume state its last stop left behind, and after a `step_over`/`step_into` that state is still "stepping", so the thread single-stepped with no debugger attached and the process died with `STATUS_SINGLE_STEP` (`0x80000004`) — measured every time on Windows 11 with CodeLLDB 1.11.8 (LLDB's `ProcessWindows::DoDetach` since LLVM PR 115712), on `detach_from_process` and on `close_debug_session` alike. For C/C++ and COBOL attach sessions (and any C/C++, Rust or COBOL launch detached with `detach_from_process`) the proxy now sends a DAP `continue` on the last stopped thread ahead of every attach-mode `disconnect` — the session's detach, the close's auto-detach and the shutdown path — and the detach result reports `data.resumedBeforeDetach: true`; if the debugger refuses the continue the detach still proceeds and `data.warning` says why the target may not survive. The session's own `disconnect` is also no longer followed by a second one from the worker's shutdown (#763)
