**Concurrent launch-shaped calls on one session are refused instead of tearing each other down** — `start_debugging` and `attach_to_process` had no in-flight guard beyond the session state and `restart_debugging`'s own reentrancy guard (#238) caught only a second restart, so none of the three saw a call of a different shape — and the state cannot tell "a launch is being awaited" from "the program is running": a JavaScript launch projects `running` the moment its child session is adopted while `start_debugging` is still parked on the launch barrier. A second call in that window passed the guard, disposed the barrier the first call was awaiting, and both returned `success: true` for a proxy that was being torn down. One in-flight claim per session, shared by launch and attach and taken before the first await, now answers the second call with *"A launch is already in progress for this session … wait for it to complete before calling restart_debugging"*; a sequential second `start_debugging` still supersedes the first launch as before, and a session left `initializing` by a readiness wait that hit its ceiling can be restarted again — the state-based check had refused it forever. `detach_from_process` takes the same claim, because it tears the proxy down just as thoroughly: a detach that landed during a parked launch stopped the worker out from under the readiness wait, which then read the worker's exit as the program finishing and reported a clean run to completion for a process the caller had just detached from (#711)
