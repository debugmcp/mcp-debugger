**One debugger core per `http` process: every MCP client sees the same debug sessions.** A Streamable HTTP server used to build an isolated server per MCP client session, so `list_debug_sessions` listed only the caller's own sessions and another client's id was refused with "belongs to another MCP client session" (#939). The 2026-07-28 revision of the protocol has no client sessions to key that on, so the model is now the one the spec names — the handle is the capability: a debug session is addressable by whoever holds its id, `list_debug_sessions` is the whole process's list, and several agents against one `http` process see each other's sessions (one process per agent is the isolation, as `stdio` already gives). Debug sessions therefore outlive the MCP session that created them, and a client that reconnects can list and resume or close what it left behind. The seam for real isolation is in place: a session is created in its caller's scope — the authenticated principal when the request carried one, otherwise the shared anonymous scope — and a session outside the caller's scope does not exist for that caller — every tool answers it exactly as it answers an id nobody holds; no authenticated `http` mode ships yet (an authenticating reverse proxy does not identify callers to the server), so every caller is anonymous and sees everything, which is today's single-tenant behaviour. `GET /health`'s `details[]` no longer carries a per-client `debugSessions` list; the process-wide `debugSessions` array replaces it. `GET /health` now lists the process's debug sessions beside the MCP sessions, and says whether a client is attending. The ten-per-language adapter cap is per process now, as it always was on `stdio`, and its refusal says how to find and close the sessions holding the slots. Step 2 of #1025.
