**A JavaScript step lands where your code next runs, and is no longer lost in Node's own code.** `step_into` on a line that calls a Node builtin took about 6 s on a Linux host and answered `pending`, blaming "a long-running call"; on the first `console.log` of a process it never landed at all and the program ran to its end. js-debug's own "smart stepper" was deciding where such a step ends: while the step was in skipped code it stepped again by itself, one engine step per statement (131 for one `console.log`), with a flag that moves the step to a later task and loses it. That stepper is now off for every session, and the server steps through skipped code itself, over js-debug's raw CDP socket, for `step_into`, `step_over` and `step_out` alike. A `step_into` that lands in skipped code walks on, one engine step at a time, until your code is on top again or the walk reaches one of its two bounds, 512 engine steps or 3 s, whichever comes first; then it steps out. A `step_into` on a line that calls your own function through skipped code (an `on` or `once` event listener behind `emitter.emit`, an array callback, a route handler from inside express) lands in that function when the walk reaches it inside those bounds; on a line whose call stays in skipped code (`console.log`) it lands where the call returned, and when the walk ended on a bound first, the message says how far it went and which bound ended it (`Stepped into. step_into walked 60 engine steps into the call and was still in skipped code … when the walk reached its 3 s limit, and stepped out …`, a later `console.log` on Linux) and that code of yours the call runs further in or only schedules did not stop the step; a pause in your code on the line the step started from is where it stops (the line's next statement, or a one-line loop's header in its first iteration); on a line that only starts a later task (`setTimeout`) it lands on the next line instead of inside the callback some time later. A `step_over` or `step_out` that returns into skipped code steps out to the nearest frame of your program below; when nothing of your program called or awaits the function (the last line of a request handler, a timer callback, a `.then` callback) the program is resumed rather than walked through the internals of later tasks (a callback of yours already queued behind a `.then` callback is where V8's own step stops), and on a launch the pending answer then says the step left its frame (a step still executing, such as a `step_over` of a long call, gets no such sentence). What counts as skipped is still js-debug's own verdict, asked at every landing, so `justMyCode`, your `skipFiles` and source maps decide it as before, and in a bundle your own lines stay program code after a stop in a bundled dependency; `justMyCode: false` (or `smartStep: false`) still lands every step where V8 lands. A forked child steps the way its root session does, launched or attached. Changed on purpose: a pause asked for while a step is still pending is reported as the pause, where the program is, and is not stepped away from; and the sentence a pending step carries no longer mentions js-debug's stepper. On Linux every engine step costs about 44 ms whoever sends it (#1163), so there the walk's 3 s bound comes first, at about 60 engine steps: a `step_into` on a `console.log` line answers in about 3.7 s there, and a function of yours that Node's code reaches only further in than that is not entered. Not fixed here: a `step_into` on a `require` line does not land where the call returned (Node's loader returns through `try … finally`, one of the steps V8 itself loses, #1161): the first load of a module of yours is lost, and in the measured cases of a built-in or already loaded module the step stops further down the same function, with the lines between run, as before; `step_over` on such a line lands on the next one.
