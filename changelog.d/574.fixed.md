**`pause_execution` and the step tools no longer report "still running" for a stop they already saw** — several related races in the execution controller's grace windows. A `stopped` event that landed inside the 5 s window but was still resolving its location when the timer fired lost to the timer, so `step_over`/`step_into`/`step_out` returned `pending: true` with "still executing" and no location, and `pause_execution` returned `pending: true` with the false message "no 'stopped' event within 5s" and without `stopReason`/`rawStopReason`/`location`; both timers now stand down once the stop has been observed, and a debuggee that ends during that same window no longer overwrites the answer with "Session ended before pause took effect" for a pause that demonstrably took effect. A pause delivered while mcp-debugger was auto-discovering a thread id settled through a separate branch that returned a bare `Paused` with no location and — because the comparison snapshot was taken after that discovery request — no stop reason either; that branch now reports exactly what the event path reports, holds the answer for as long as its own stack read takes, and leaves the internal pause flag clean instead of stranding it armed for the rest of the session. A session that terminated during the same discovery request made `pause_execution` fail with an internal `TypeError` instead of the `Cannot pause: no active proxy for session <id>` failure the identical pre-flight check reports. Finally, a step whose debuggee exited or terminated mid-step reported "Stepped over" over the top of the controller's "Step completed as session terminated." — the real message now survives (#574)
