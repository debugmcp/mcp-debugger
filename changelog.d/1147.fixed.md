**A breakpoint set on a running session reaches the debug adapter in the same form as one set before the launch.** On Windows, a .NET breakpoint set on a running session with a forward-slash path never bound (`No symbols have been loaded for this document`), while the same path set before `start_debugging`, or typed with backslashes, did. The launch sent `path.resolve` of the path and a file name; a live request sent the path as typed. Both now build the DAP `source` one way: a path of the server's own machine goes out in that machine's spelling, and a path that is not absolute there (the debuggee's own path in a remote attach) goes out as given, where the launch used to turn `/app/main.py` into `C:\app\main.py`. A file named under two spellings is one set of breakpoints to the adapter, so setting one spelling no longer clears the other's, and `list_breakpoints` no longer reports a `boundFile` that is only another spelling of the breakpoint's own file.
