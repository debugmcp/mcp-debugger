**The unarmed launch answer no longer promises an uncaught-exception stop the adapter cannot deliver** — a Ruby launch with no `breakOnExceptions` (rdbg has no uncaught-only filter, so nothing is armed) and a C/C++ launch on Windows (abort() ends the process with exit code 3; the SIGABRT stop is a POSIX fact) said the program "will stop only for an uncaught exception the debugger catches by default", then reported the exit. The verdict is now recorded beside the filter ids the mode actually armed, from the policy's own table — `'none'` opted out, no filter available, or (an attach with no mode) none requested — and the launch and `wait_for_stop` pending answers say which, promising only the exit. An explicit `breakOnExceptions` the adapter resolves to no filter (`"uncaught"` on Ruby) now adds a `warning` naming the modes it does support instead of being a silent no-op; the policy default never warns. The cpp policy pins `stopsOnUncaughtWithoutFilter` per platform, and the cross-policy contract test requires that pin from any policy whose `uncaught` table is empty under an `'uncaught'` default (#1032; follows #1009)
