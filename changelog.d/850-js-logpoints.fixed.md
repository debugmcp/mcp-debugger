**JavaScript logpoints are delivered by mcp-debugger, not by the program's `console.log`** — js-debug compiles a logpoint into a `console.log(...)` call evaluated inside the debuggee, so a program that had replaced `console.log` (mcp-debugger's own stdio server does, to protect its protocol stream) lost every logpoint silently: `verified: true`, nothing in `get_output`, no hint why. The JavaScript policy now compiles the `logMessage` itself into a breakpoint condition that renders the message (strings raw, other values through `util.inspect`, a throwing `{expr}` shown inline as `<ReferenceError: …>`), hands it to a binding the proxy installs over js-debug's CDP proxy (`Runtime.addBinding`), and returns false so the program never pauses; the message arrives as a `console` entry in `get_output` and the output resource, whatever the program did to `console`. A logpoint that also carries a `condition` logs only when the condition holds instead of pausing (js-debug compiles the condition first and drops the message, #861). A pre-launch logpoint makes js-debug stop on entry so the binding is installed before the first hit; the SessionManager auto-continues that stop as it does for function breakpoints. The stored breakpoint keeps the user's `logMessage` and `condition`, so `list_breakpoints` and `restart_debugging` are unchanged (#850, #861)
