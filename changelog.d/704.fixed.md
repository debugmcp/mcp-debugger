**A JavaScript launch of a program that does not stop answers promptly and is left alone** — with `stopOnEntry: false`, `start_debugging` for an idle server came back only when the js-debug launch barrier gave up, because a js-debug launch never produced the configured status the barrier and the readiness wait listen for; 15 s in, the child-session adoption misread the launch as wanting an entry stop (the caller's `stopOnEntry` never reached it) and paused the debuggee itself, and on an idle server that pause landed on Node's next timer tick inside its internals, where js-debug's smart-stepper single-stepped the program 261 times in 30 s and twice more on every tick after. The launch now threads the caller's `stopOnEntry` into the child adoption (and always sends a boolean), so the forced pause never happens; the worker reports the configured status once the child is adopted, and the launch barrier treats it as ready after a short window for a first stop that may already be in flight, so an idle server answers `state: "running"` about a second after the launch and a breakpoint on a module-load line still reports `paused`. With the forced pause gone, a user's own `pause_execution` can be the first stop of such a launch; it is never auto-continued as an entry stop (#704)
