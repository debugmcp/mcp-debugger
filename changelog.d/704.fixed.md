**A JavaScript launch of a program that does not stop answers promptly and is left alone** — with `stopOnEntry: false`, `start_debugging` for an idle server came back only at its 30 s ceiling, because a js-debug launch never produced the configured signal the readiness wait listens for; 15 s in, the child-session adoption misread the launch as wanting an entry stop (the caller's `stopOnEntry` never reached it) and paused the debuggee itself, and on an idle server that pause landed on Node's next timer tick inside its internals, where js-debug's smart-stepper single-stepped the program 261 times in 30 s and twice more on every tick after. The launch now threads the caller's `stopOnEntry` into the child adoption, so the forced pause never happens; the worker reports the configured status once the child is adopted, so an idle server answers `state: "running"` in about half a second; and that signal waits a short grace for a first stop that may already be in flight, so a breakpoint on a module-load line still reports `paused` (#704)
