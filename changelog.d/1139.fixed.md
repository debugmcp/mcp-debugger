**A Python or Ruby attach to a port that does not speak DAP now says so, instead of describing an adapter that never existed.** These attaches start nothing: the server connects straight to the host and port given, so "the adapter" is whatever listens there. Attaching to a listener that accepts the connection and stays silent — the wrong port — waited 30 s and answered "…an adapter-side protocol stall, not a missing install — the adapter started and accepted the connection. Retrying usually succeeds", and retrying stalled identically. Attaching to a real HTTP port (the application's own, say), which hangs up on the DAP frame, answered "Critical initialization error: DAP client disconnected [Executable: python | adapter PID=none exitCode=n/a]". Both now name the endpoint and the likely cause: "127.0.0.1:5000 accepted the connection but never answered the DAP "initialize" request. Nothing was started for this attach: the server connected to what is already listening on that port, so check that it is a debugpy listener (python -m debugpy --listen 127.0.0.1:5000 …) and not another service. Retrying the same port stalls the same way." Once the endpoint has answered `initialize` it is a debug server, and a later stall is worded as its own; a connection that was never made no longer says to check that the adapter is installed. The failed answer's `data.initProgress` gains `directConnect` (`host`, `port`, `listener`). The spawned-adapter messages are unchanged, and so is the 30 s deadline. (#1139)
