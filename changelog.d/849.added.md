**`wait_for_stop`: block until a session next pauses or ends, instead of polling** — a 29th tool. `continue_execution` returns as soon as the adapter acknowledges the resume, and `start_debugging`, the step tools, `pause_execution` and `attach_to_process` answer `pending: true` when the stop they were waiting for has not arrived; until now the only way to learn about the later stop was to poll `list_debug_sessions`. `wait_for_stop {sessionId, timeout?}` blocks until the session is paused (answering with the same `lastStop` record the session listing shows, plus the top frame's `location` and source line) or over (the terminal state, with `exitCode` when the debuggee reported one). A session that is already paused or already finished answers at once; `timeout` (ms, default 30000, max 600000) bounds the call, not the program, and a wait that runs out answers `state: "running"` with `pending: true` so it can simply be called again. The wait is on the session's state rather than on the adapter's raw `stopped` event, so the entry stop a `stopOnEntry: false` launch resumes by itself is never reported, and a call the client cancels releases its wait. Every existing `pending: true` message and the affected tool descriptions now say that nothing was cancelled — breakpoints and exception filters stay armed, a step or pause is still in effect — and name the tool (#849)
