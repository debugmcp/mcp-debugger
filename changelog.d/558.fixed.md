**JavaScript block-scoped bindings are visible as locals** — a `let`/`const` declared inside a `for` body, an `if` block or a `catch (e)` clause lives in a js-debug scope named exactly `Block` (or `Catch Block`/`With Block`), while mcp-debugger only recognised the `Block:<label>` form some builds emit — so `get_local_variables` at a breakpoint inside a loop silently omitted the loop variable. Every block scope on the frame is now merged ahead of the function's own `Local` scope, innermost first, matching JavaScript's shadowing order; nested blocks (a `catch` inside a `for`) all contribute, where previously only the first one did. The response keeps naming the `Local` scope with no note whenever the frame has one — including when `Local` itself contributed nothing because it held only `this` or because a `names` filter emptied it, which previously produced a note blaming `Local` for a fall-through that never happened. On an ESM top-level frame (block scopes but no `Local` at all) the module's own bindings join the merge as the frame's base, so they are still reported as they were before block scopes were recognised, and the response names the block. Global remains reserved for frames with no local or block scope at all (#558)
