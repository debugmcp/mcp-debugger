**JavaScript attach by `processId`** — `attach_to_process { processId }` on a JavaScript session now attaches to a running Node.js process that was not started with `--inspect`: the adapter does what VS Code's process picker does (js-debug's own DAP server has no PID step) — it signals the process (`SIGUSR1`, or `process._debugProcess` on Windows), which opens its inspector on `127.0.0.1:9229`, confirms through the inspector's `/json/list` that the port belongs to that PID, and attaches there; `port` alongside `processId` names where a `--inspect-port=<n>` target opens. Previously the PID was silently dropped and js-debug dialled `localhost:9229` on its own, so the tool answered a generic "adapter exited during attach verification (code=null)". Refusals name their cause: a non-loopback host, the server's own PID, a PID that is not a Node.js process or was started with `--disable-sigusr1` (both checked before signalling on POSIX, where `SIGUSR1` would terminate the process), a port held by another process's inspector or by a debugger that holds the target paused, a host PID from inside the container, and — new for every JavaScript attach — a request with neither `port`, `processId` nor `websocketAddress` is rejected up front instead of being sent to js-debug port-less (#871)
